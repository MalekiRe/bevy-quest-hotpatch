# bevy-quest-hotpatch

**Live hot-patching for Bevy apps on Android / Quest (built with `cargo apk`) — no app restarts.**

> ⚠️ **This project was AI-generated by DeepSeek-V4-Flash.**

Edit your Bevy game's code, save, and see the change appear in the running app in a fraction of a second —
on a phone or a Quest headset (OpenXR). It patches the already-running process in place using the
[`subsecond`](https://github.com/DioxusLabs/subsecond) jump-table machinery, driven by your own dev-server.

---

## Highlights

- **Live patches single source-file edits** to the running APK (phone and Quest).
- **Two hot-patch styles** — pick whichever fits:
  - **Bevy's native hotpatching** (`bevy` feature `hotpatching` → `HotPatchPlugin` is wired into `DefaultPlugins` automatically). Edit any system body; bevy re-points it at runtime.
  - **`with_hot_patch`** — register systems inside a closure that re-runs on each patch. Macro-free.
- **Full unfiltered jump table** — every symbol that changed in the tip crate is remapped, with no hand-maintained filtering.
- **`cargo` integrated** — the toolchain is a `cargo` subcommand: `cargo quest-hotpatch build|install|serve`.
- **Workspace-aware** — build artifacts and captures are found under the correct workspace target root automatically.
- **OpenXR/Quest ready** — the same patch engine drives `cargo apk build` apps, including the bundled `oxr-app`.

## Prerequisites

- Rust (edition 2024) + [cargo-apk](https://github.com/rust-mobile/cargo-apk)
- Android SDK + NDK (`ANDROID_HOME`, `ANDROID_NDK_HOME` set)
- A phone or Quest 3 with **wireless adb** or USB, and an app that sets
  `android.permission.INTERNET` (cargo-apk adds no permissions by default)
- **bevy 0.19**, `cargo apk build` as the build path (required for OpenXR `runtime_libs`/Quest manifest)

## Quick start

```sh
# 1. Build the toolchain (the CLI binary + rustc/linker capture shims)
cargo build -p cargo-quest-hotpatch --bins

# 2. Build the app APK (with symbol capture) and install + launch it on the device
cargo quest-hotpatch --app-dir app --device <ip>:5555 build --deploy
```

Then, in a second terminal, run the dev-server:

```sh
cargo quest-hotpatch --app-dir app serve
```

The app connects to `ws://127.0.0.1:8080/_dioxus` (via `adb reverse tcp:8080`) on startup.

**Hot-patch it:** open `app/src/lib.rs`, change the marker/color, save —
the running app picks up the change in under a second.

## `cargo quest-hotpatch` CLI

```
cargo quest-hotpatch <subcommand> [options]
```

| Subcommand | Purpose |
|---|---|
| `build` | `cargo apk build` with capture shims (fresh baseline for patching). `--deploy` also installs + launches. |
| `install` | adb install + launch the existing APK. |
| `serve` | Watch `src/` + run the dev-server; tip-crate edits are hot-patched, anything else triggers a full rebuild. |

Global options:

| Flag | Default | Meaning |
|---|---|---|
| `--app-dir <path>` | `.` | Directory holding the app crate (`Cargo.toml` with `[package.metadata.android]`). |
| `--crate <name>` | auto-detect | Rust `[lib]` name of the app crate. |
| `--device <serial>` / `DEVICE` | first device | adb serial (e.g. `192.168.1.151:5555`). |
| `--package <name>` | `dev.malek.questhotpatch` | Android package name. |
| `--activity <name>` | `android.app.NativeActivity` | Launcher activity. |
| `--port <n>` | `8080` | Dev-server port (must match the app’s `/_dioxus` dial). |

## Hot-patch styles

### 1. Bevy native (`hotpatching` feature)

Enable the feature on the `bevy` dependency:

```toml
bevy = { version = "0.19", features = ["android-native-activity", "hotpatching"] }
```

`DefaultPlugins` then includes `bevy::app::HotPatchPlugin`, which connects to the dev-server and
applies incoming jump tables. Systems are re-pointed automatically — edit any system body:

```rust
fn probe(time: Res<Time>, mut last: Local<f32>) {
    if time.elapsed_secs() - *last > 3.0 {
        *last = time.elapsed_secs();
        info!("marker=BEFORE"); // change BEFORE -> AFTER and save
    }
}
```

### 2. `with_hot_patch`

Register systems inside the closure; it re-runs on each patch and hot-swaps them into the running
app. No macro needed, and **no hardcoded schedule list**: the closure can use *any* schedule
(built-in or custom). Each schedule it touches gets a mirror (from a pool of 1,000) plus a proxy in
the real schedule, discovered and wired at runtime:

```rust
App::new()
    .add_plugins(DefaultPlugins)
    .add_plugins(quest_hotpatch::prelude::SimpleSubsecondPlugin::default())
    .with_hot_patch(|app| {
        app.add_systems(Update, paint_cube); // plain fn — edit its body to recolor
    })
    .run();
```

## How the patch is built (brief)

On `serve`, saving a `lib.rs` triggers a **thin rebuild** of only the tip crate (dependencies are
cached), producing a fresh object. The engine:

1. rebuilds the tip crate’s object (deterministic `-C metadata`),
2. generates stubs for any host symbols the patch references (jumping to their runtime addresses),
3. links the patch `.so` with the NDK clang (reusing the captured fat link arguments),
4. diffs the original vs. patch symbol tables into a **full jump table** (all changed Text symbols),
5. serves it to the app, which `apply_patch`s it via `android_memmap_dlopen`.

The app anchors ASLR on `main`; the jump table and the generated stubs both use that same anchor.

## Quest 3 (OpenXR)

The `oxr-app` directory is a `bevy_oxr` OpenXR demo that uses the same engine. Build/install it the
same way, pointing `--app-dir`/`--crate` at it:

```sh
cargo build -p cargo-quest-hotpatch --bins
cargo quest-hotpatch --app-dir oxr-app --crate quest_oxr_app --device <quest-ip>:5555 build --deploy
cargo quest-hotpatch --app-dir oxr-app --crate quest_oxr_app --device <quest-ip>:5555 serve
```

The Quest app drops its OpenXR loader into `runtime_libs` (via `cargo apk`), which the `dx` CLI
cannot bundle — this toolchain keeps `cargo apk build` as the build engine for that reason.

## Troubleshooting

- **App never connects** — start the dev-server, then relaunch the app (it dials the dev-server once
  at startup). `adb reverse tcp:8080 tcp:8080` must be active.
- **Nothing changes on edit** — confirm the app is running the latest `build --deploy` baseline (the
  host diffs against the last captured build).
- **Patches crash with SIGSEGV/SIGTRAP after a toolchain update** — rebuild everything with
  `cargo build -p cargo-quest-hotpatch --bins` and run a fresh `build --deploy` so the captures and
  the deployed binary match.
